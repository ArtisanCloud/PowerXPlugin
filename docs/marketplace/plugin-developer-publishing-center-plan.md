# PowerXPlugin 开发者发布中心与市场对接方案

版本：0.4。日期：2026-11-09。状态：F02 与 F03 首个构建配置已实现并受控验证；实际 Linux/Nuxt 运行验收及正式市场契约待补，M1 尚未完成。

本文与 PowerXPlugin 仓库同路径文档维护同一正文，源码和关联文档链接按所在仓库换算。两端共同使用[实现设计与交付范围](plugin-publisher-implementation.md)，第 18 节记录逐项对齐结论，第 19 节记录文档交付与剩余工作。修改任何一份时同步另一份；两端不各自维护不同的协议或验收矩阵。

PowerXPlugin 提供统一的开发者发布中心，让通过 Framework 开发的插件可以在开发管理页面创建版本、执行构建打包、上传到 PowerXPluginMarket，并查看审核状态。构建执行器运行在具有源码和工具链的本地开发环境或 CI；市场负责开发者授权、制品接收、版本登记、审核与分发。

第一期完成一个插件、一个目标平台的“版本草稿 → 构建 → 上传市场草稿 → 状态回显”。第二期接入提交审核。多平台批量构建、beta 渠道和 CI 自动化在后续阶段扩展。上传、提交审核、批准、公开上架分别呈现状态。

当前新增的 Go CLI `publisher plan create/list/get` 与 `publisher serve` 已实现；本地接口见[Framework 本地工具契约](../contracts/plugin-publisher-local-v1.md)。F03 已增加隔离构建、冻结 ZIP、摘要复核、所属进程组取消与中断恢复，详见[隔离构建契约](../contracts/plugin-publisher-build-v1.md)。首个配置只接受原生 Linux/amd64、无 CGO 的 Go 后端和纯 JS 前端；macOS 拒绝构建，受控 fixture 不等于实际 Linux/Nuxt 验收。上传、送审及页面尚未交付。

本文中的“现有”指第 2 节列出的源码行为；其余内容为已统一的实现方向及待冻结的机器契约草案。文档对齐不等于市场正式 OpenAPI 已冻结，也不表示发布凭据、页面或真实上传链路已经交付。

阅读顺序：先核对第 2 节现状和第 18 节对齐结论，再按第 7 至 12 节及实现设计补齐正式契约。PowerXPlugin 从第 14 节领取任务，市场从第 15 节领取任务，联合验收使用第 17 节。

## 1 产品目标与使用边界

### 1.1 开发者需要完成的任务

1. 查看当前插件的源码版本、本地构建和市场版本，判断下一步操作。
2. 创建待发布版本，填写更新说明，选择构建目标和目标市场。
3. 点击“构建并上传”，看到各阶段进度、错误原因和市场草稿链接。
4. 在资料齐备后提交审核，继续查看待审、驳回、批准和上架状态。
5. 重试失败阶段时复用已确认的构建或上传结果，避免重复操作。

页面应使开发者清楚知道：哪个源码快照构建了哪个平台包、字节是否已经被市场保存、当前版本是否公开。开发者不必手动复制存储路径或操作市场数据库。

### 1.2 开发环境与客户安装环境

| 环境 | 开发者发布中心的行为 |
| --- | --- |
| 插件源码开发环境 | 显示开发者入口，连接本地发布执行器，允许授权范围内的构建与上传 |
| CI | 使用同一构建及发布引擎，通过非交互入口执行，不依赖页面 |
| 客户 PowerX 中安装的插件 | 不挂载开发构建入口及命令执行接口；版本信息和检查更新沿用运行态能力 |
| 开发者在 PowerX 中调试插件 | 仅在明确启用的开发工具环境中进入发布中心；宿主管理员身份不自动取得市场发布权限 |

发布中心作为 Framework 的公共开发工具交付，业务插件仅提供插件身份、构建配置和发布资料。第一期不要求每个插件各自开发一套构建后端。

### 1.3 首版范围

- 支持一个已在市场登记、归属当前开发者的插件。
- 支持一个执行器实际可构建和校验的目标平台，优先验收 Linux 执行器上的 `linux/amd64`。
- 支持正式 SemVer 版本、`stable` 渠道、本地版本草稿和更新说明。
- 支持构建产物校验、真实文件上传、幂等恢复、市场版本查询及跳转。
- 市场新增适合本地工具的发布授权，保留现有浏览器登录及 CSRF 规则。

第一期不包含自动注册市场开发者、自动占用插件 ID、远程代管源码、Git 提交或打标签、公开上架自动批准、客户实例升级、数据库迁移执行、付费许可与结算。后续增加 CI 入口也不等于授权触发用户仓库的构建工作流。

## 2 当前基础与需要补齐的差异

源码核对日期为 2026-11-09。市场工作区 HEAD 为 `c863f284fc1c`，Framework HEAD 为 `32aaf0bd33ec`；对齐开始时市场已有本方案及文档入口改动，Framework 已有其他未提交改动。下列结论描述核对时工作区源码，不将工作区当作已发布 SDK、生成器或已部署市场版本。

| 能力 | 当前源码行为 | 本方案需要补齐 |
| --- | --- | --- |
| Framework 本地工具 | 新增 Go CLI publisher 计划创建/分页/读取及独立回环服务，UUID 计划原子落盘、一次性握手和短期工具会话已受控验证 | F03 首个配置已受控验证，实际 Linux/Nuxt 运行待验；F04 市场客户端及 F05 页面代理未实现 |
| Framework 构建 | `make dist` 构建后端及前端，向产物 `plugin.yaml` 写入版本和 `target`，校验 Go 二进制目标；`make package` 再生成 ZIP | 可追踪任务、隔离输出、页面进度、完整运行时的平台校验 |
| Framework CLI 发布 | Go CLI `publish` 读取 `.px-plugin/build` 产物，向 `/internal/plugins/releases` 发送 JSON，`buildArtifactUri` 来自本地文件 URI | 面向开发者市场接口发送真实包字节，统一版本与产物身份 |
| Framework TypeScript 发布 | `executePublishPipeline` 在本地生成 ID 和固定域名上传地址，没有发送安装包；Plan/Deploy 示例也不等于市场持久化发布闭环 | 新发布只使用 Go 共享引擎；旧测试不能作为真实上传、签名或送审证据 |
| Framework 打包入口 | `make package` 压缩 dist 为 ZIP；Go package Builder 另行组织 payload 并生成 TAR；Go `px-plugin dist` 当前只提示 experimental | 统一冻结目录和打包校验，不把三个入口当作同一实现 |
| 市场开发者页面 | 已有插件、版本、平台包、上传、发布记录和提交审核入口 | 发布工具的机器接口、细粒度授权、稳定的恢复回执 |
| 市场上传 | `/dev/plugins/:plugin_id/package` 接收 multipart 文件、更新说明、OS 和架构，最大包大小 2 GiB | 版本和校验值显式核对、幂等写入、发布工具专用响应 |
| 多平台数据 | 同一语义版本可保存不同 OS/arch 的 Artifact；同平台重复上传返回冲突 | 批量构建、完整目标集合快照、逐包验证与恢复 |
| 身份认证 | 市场 `Require` 支持 Cookie 或 Bearer，但 Bearer 仍解析市场登录会话；开发者状态和资源归属由服务端检查 | 独立发布凭据、插件及操作范围、到期与撤销 |
| 渠道 | 开发者上传服务创建版本时写入 `stable`；稳定渠道上架拒绝预发布版本 | 后续显式渠道契约；第一期不显示尚不可用的 beta 操作 |
| 审核与上架 | `draft/rejected → submitted → approved/rejected → published`；人工批准与上架分开 | 发布工具读取同一状态源，不能另建可绕过审核的状态机 |
| 包校验 | 上传解析包内插件 ID 和版本并计算摘要；提审及上架复核主制品；安全门禁检查已有报告 | 全部平台包的一致性复核；缺少扫描报告不得显示为扫描通过 |

当前上传允许在 `draft` 或 `rejected` 版本上追加尚不存在的平台包，已提交、已批准或已发布版本禁止追加。同版本同平台的包不能覆盖。草稿删除还要求未被提交或引用，不能把“被驳回”理解为可自由删除。

`px-plugin publish` 的本地文件 URI 不是对远端市场的文件传输。对齐时必须同时处理接口、认证和包内容，不能只把现有命令挂到页面按钮上。

## 3 系统职责与数据权威

| 对象或动作 | PowerXPlugin Framework | PowerXPluginMarket | PowerX Core |
| --- | --- | --- | --- |
| 页面及本地任务 | 提供开发者入口、任务执行器、CLI、日志和本地恢复 | 提供市场控制台及版本详情入口 | 首期无新增职责 |
| 构建及打包 | 读取源码，执行构建，校验运行时目标，生成安装包 | 接收并独立核对包、摘要和登记信息 | 后续按既有安装契约验收 |
| 市场身份 | 安全保存凭据引用，使用发布授权 | 签发、查询、撤销授权并核对开发者与插件归属 | 宿主身份不替代市场身份 |
| 本地版本草稿 | 保存计划和构建记录 | 首期上传成功时创建市场草稿 | 无 |
| 市场版本及平台包 | 查询、比对，保存回执 | 维护唯一记录、锁定规则及完整性 | 读取可分发的已上架版本 |
| 审核及公开上架 | 提交资料、展示服务端状态 | 审核、批准、上架及审计的权威来源 | 不参与市场独立审批 |
| 客户安装及升级 | 不由发布工具代执行 | 按既有机制提供目录及下载 | 负责安装事务、启用和结果回报 |

市场 `developer_id`、市场用户 ID 和 PowerX 业务租户 ID 分属不同用途。发布请求不得用客户端提交的租户、用户或 `vendor_id` 替代服务端解析出的市场归属。

首次文档对齐仅统一两仓库方案和指南。随后按用户执行指令在 PowerXPlugin 当前分支实现 F02 本地工具及 F03 首个构建配置；市场功能代码、Core、数据库及日常服务未修改，两边文档同步记录进度。后续源码、生成器、接口部署及真实市场写入分别记录实现和执行范围；本文的任务分工不自动授权操作其他插件或 Core。

## 4 页面组织与交互

### 4.1 概览与分区

开发者发布中心顶部显示插件名称及 ID、源码声明版本、当前选中发布版本、目标市场、最近任务阶段和市场状态。默认进入版本管理；首次未连接市场时保留本地创建与构建入口，在顶部提示连接要求。

桌面使用左侧纵向 Tab 导航和右侧当前内容，窄屏切换为可操作的紧凑分区导航。错误、授权失效、维护状态和运行中任务摘要始终可发现。

| 分区 | 当前任务内容 | 详情入口 |
| --- | --- | --- |
| 版本管理 | 本地草稿和市场版本列表，创建版本、选择当前版本 | 抽屉查看更新说明、来源、平台包和审核详情 |
| 构建打包 | 当前版本、可用执行器及平台、构建主操作、当前任务进度 | 日志面板、校验报告、产物摘要 |
| 上传与审核 | 当前产物与市场状态、上传或送审操作、资料完整性 | 资料表单弹层、审核记录抽屉、市场详情链接 |
| 市场连接 | 市场地址、已绑定开发者、授权范围及到期时间 | 授权说明、撤销和重新绑定入口 |

列表和日志可以自然滚动。各分区不能重新堆成单个长页。切换分区保留选中版本、草稿、正在进行的任务和错误；刷新后从执行器恢复任务，再读取市场当前状态。

### 4.2 操作语义

- “创建版本”创建本地计划，首期不提前在市场创建空版本。
- “仅构建”不需要市场网络，工具链与本地配置必须就绪。
- “构建并上传”先校验发布授权、插件归属、版本和目标，之后构建并上传；已有可复用且校验通过的冻结产物可进入上传阶段。
- “上传已有产物”复用明确选中的本次产物，展示版本、平台、大小和摘要，不自动取目录中的“最新文件”。
- 第二期提供“上传后提交审核”，默认关闭。用户选择后只自动送审，人工审核和公开上架沿用市场流程。
- “查看市场版本”打开已配置市场返回的受信详情地址。上传完成提示使用“已上传为市场草稿”；送审完成提示使用“已提交审核”。

按钮显示其不可用原因，例如平台不受支持、凭据到期、版本已锁定、资料不完整。对已有成功阶段的“重试”仅执行失败或结果待核对的步骤。

### 4.3 组件和偏好

双方各自使用所在项目实际安装版本的 Nuxt UI。核对时市场依赖声明为 `@nuxt/ui ^2.7.1`，Framework Skeleton 为 `3.3.7`，两端共享交互规范和数据契约，不直接复制不同版本的组件 props、插槽和事件。

主题沿用 `useColorMode`，语言沿用现有 i18n，支持刷新恢复。验收覆盖桌面、窄屏、浅色、深色、键盘、菜单、语言、状态保留及 SSR/hydration 日志。

正文、标签、状态、按钮和弹层均使用主题语义颜色；普通文字对比度至少 4.5:1，大字号文字至少 3:1。实际渲染手动主题与系统主题不一致的组合，以及默认、悬停、选中、聚焦和禁用状态。所有用户可见文案和测试中的文案断言走 locale；错误按稳定 code 和结构化参数映射文案，不解析自由文本。对象 UUID 用作请求及诊断标识，界面优先显示名称、版本和平台。

## 5 本地执行架构

发布中心由“Framework 开发态页面 + Go CLI 本地执行器 + Go 共享发布引擎”组成。页面通过开发服务器同源代理访问回环执行器，CLI 非交互入口使用同一引擎；TypeScript 只承担页面客户端或测试工具职责。已交付 plan、serve、build run/get/list/verify/logs 命令及 /v1 计划、构建、会话路由；页面代理及市场命令尚未交付。本方案不向业务插件 HTTP 服务增加构建接口。

生产构建不注册发布页面、菜单及开发代理，安装包不包含执行器、工具会话及市场凭据。验收分别直接访问页面和请求执行接口，不能以菜单隐藏或 `dev` 布尔值证明边界成立。

调用顺序：

1. 开发者从插件开发导航进入发布中心，页面取得本地工具会话。
2. 执行器读取当前受信工作区、工具链和市场连接配置。
3. 页面提交结构化版本计划，执行器校验字段并创建持久化任务。
4. 共享引擎依次执行预检查、构建、打包、校验和上传。
5. 执行器将本地任务事件反馈页面，将市场操作回执落盘。
6. 页面读取市场版本及审核状态，显示准确的结果和下一步。

浏览器不直接执行 `make`。执行器仅绑定回环地址，检查允许的 Host、Origin 和短期本地工具会话；仅绑定 localhost 或启用开发开关都不能替代请求授权。通过用户明确启动的受信源码工作区执行固定任务，页面不能指定任意 shell、可执行文件或工作目录。

版本、平台和路径分别校验，使用参数数组调用命令。禁止拼接 shell 字符串；版本中即使没有 shell 特殊字符，也不能跳过 Makefile 变量及路径边界检查。执行器知道自己启动的进程及子进程，可取消所属构建，不能按端口或进程名称批量清理。

开发工具会话只授权访问本地执行器。市场发布凭据留在执行器的凭据存储中，不进入页面状态、URL、localStorage、前端 public runtime config 或插件安装包。

页面中的市场查询、上传和送审均经执行器发起，浏览器只接收脱敏 DTO。市场控制台在创建发布凭据时的一次性展示不属于插件页面的凭据传递；将凭据绑定给执行器也不能经过插件的公开前端配置。

首期进度协议固定为本地任务查询，使用有界轮询并在终态停止；这是本地工具的首选传输，不是 WebSocket/SSE 失败后的兜底。若以后改为事件传输，应单独修订契约，不静默叠加轮询。此流程不要求增加 Core TaskBus、WSBus 或宿主服务授权。

## 6 版本计划与任务数据

### 6.1 对象与标识

| 对象 | 标识及权威来源 | 关键规则 |
| --- | --- | --- |
| 插件 | `plugin_id`，包内和市场登记一致 | 显示名称不参与身份匹配；不强制第三方使用 PowerX 自有命名空间 |
| 本地计划 | `release_plan_id`，执行器生成 UUID | 创建时明确版本、目标、连接和操作意图 |
| 构建任务 | `build_id`，执行器生成 UUID | 记录完整源码提交、工作区是否有修改、工具版本和阶段；不沿用按秒时间戳目录作为任务身份 |
| 市场版本 | `version_id`，市场返回 UUID | `(plugin_id, version)` 唯一，渠道不参与该唯一键 |
| 平台包 | `artifact_id`，市场返回 UUID | 同一版本的 `(os, arch)` 唯一，逐包保存大小和 SHA256 |
| 发布申请 | `publication_id`，市场返回 UUID | 与真实版本及全部送审平台包绑定 |
| 上传或送审操作 | `operation_id`，客户端持久化 UUID | 作为机器写接口的 `Idempotency-Key`，用于结果恢复 |

`build_id`、`version_id`、`artifact_id` 和包摘要不得互相代用。`source_commit` 和工作区修改标记是来源记录，不等于签名或可复现构建证明。

### 6.2 本地持久化

本地状态目录统一为插件工作区 `.px-plugin/publisher/`，并纳入 Skeleton、scaffold 和 CLI 内嵌模板的忽略配置。记录至少包含：

- 计划、插件 ID、版本、渠道、更新说明和目标集合。
- 市场 API root、连接 ID、凭据引用；不保存凭据明文。
- 构建来源、工具版本、校验报告、产物相对路径、大小和摘要。
- 每阶段的开始及结束时间、当前状态、脱敏错误和日志引用。
- 每次市场写操作的稳定操作 ID、市场返回的版本、制品和申请 ID。

任务记录原子写入。执行器重启后不得将中断中的构建标为成功，也不自动重放可能已经送达市场的写操作；先核对市场操作及版本结果。构建来源有修改时在确认界面和记录中明确标注，不自动提交、暂存或清理用户改动。

### 6.3 构建配置示例

以下为拟议的非敏感配置形状，配置文件名称由 Framework 决定；`credential_ref` 仅为本地凭据引用。

```yaml
schema: powerx.plugin-publisher-config/v1
market:
  api_root: https://market.example/api/v1
  credential_ref: market-developer-demo
build:
  profile: make-dist-pure-go-js/v1
  target:
    os: linux
    arch: amd64
release:
  default_channel: stable
  submit_after_upload: false
```

支持多个市场连接时，每次任务固定选中的市场及凭据绑定。更改 API root 不得沿用另一市场的凭据；远端重定向也不得把 Authorization 转发到新 origin。生产连接使用 HTTPS，本地 HTTP 调试只允许明确的回环地址。

## 7 构建与安装包契约

### 7.1 统一构建入口

首版以生成插件现有 `make dist` 作为构建基础，并对同一次构建的冻结目录执行压缩。Framework 需要梳理 `make dist`、`make package` 和 CLI package Builder，统一安装包内容及校验；页面与 CLI 复用同一引擎，不能各自产生不同布局的包。

现有命令示意如下；执行器必须补充独立输出及构建隔离，不能照抄示例共享目录执行并发任务。

```bash
make dist VERSION=1.2.0 PLATFORM=linux TARGET_ARCH=amd64
```

任务选中的版本写入产物 `plugin.yaml`，默认不修改源码 `plugin.yaml`。产物中的后端版本、前端运行时版本及附带元数据应与之相符。所有平台必须来自同一个明确的源码快照；构建中源码发生变化时阻断复用，提示重新构建。

当前 Makefile 存在共享后端和前端输出路径。首期对同一工作区串行执行构建，并为任务分配独立 staging；后续并行平台构建必须隔离后端、前端和打包输出，不能只改变 `DIST_DIR` 就认定已经隔离。

### 7.2 包内容与身份

首版统一使用 ZIP 容器及 `make dist` 安装布局；新引擎只压缩已经冻结的 staging，不再次调用会触发构建的 `make package`。市场旧浏览器链路可接收的其他容器不要求新工具同时支持；`.pxp` 后缀本身不证明包格式、签名或安全性。不得在本方案中另行引入与当前宿主不兼容的 PXP 格式。

规范化打包入口只接受冻结 staging 目录。目录包含唯一的有效 `plugin.yaml`、后端及所需迁移程序、前端运行产物、`plugin.d` 声明，以及现有安装契约要求的受控资源。ZIP 中可使用单一顶层版本目录；首期不改变宿主的安装目录解释。

逐包核对以下三组值：

1. 计划中的 `plugin_id/version/os/arch`。
2. 新工具包内 `plugin.yaml` 的正式 `id`、`version`、`target.os/arch`；不新增旧 `plugin_id` 字段回退。
3. 实际可执行文件及完整运行时的目标平台。

三者必须一致。对新发布工具采用显式 `target`；历史包缺少 `target` 的兼容政策保持在既有浏览器上传链路中单独管理，不让新工具靠手工填写平台绕过目标校验。

### 7.3 完整运行时的平台验证

Go 后端及 migrate 程序通过构建信息验证 OS/arch。Nuxt/Nitro 产物中若存在原生 Node 模块，也必须匹配目标平台。跨编译 Go 成功不代表在 macOS 构建的整个前端运行产物可部署到 Linux。

执行器返回实际支持的目标集合。第一期 Linux 运行包使用能构建和验证完整 Linux 运行时的执行器；不支持的本地目标明确提示切换执行器，不能宣称操作系统枚举中的所有组合均可构建。非 Go 后端与 Windows 构建按各自完整运行时验收后启用。

### 7.4 冻结和摘要

- 上传单位为明确选中的压缩文件，计算压缩文件实际字节的 SHA256 和大小。
- 上传重试复用原文件；即使源码未变，也不通过重新压缩生成“同一次重试”的新字节。
- 上传前和读取上传流时确认文件未变化；任务记录保存最终冻结摘要。
- 服务端独立计算流中摘要及大小，并与声明值比较。
- 构建结果可重复生成相同摘要属于额外质量目标，不能用“记录了源码提交”替代可复现构建验证。

打包使用受控清单，排除 `.env`、凭据存储、源码仓库元数据、业务数据库、上传文件、缓存和本地工具会话。不得递归复制整个工作区或 `docs`。包内不得含绝对路径、路径穿越、重复条目或逃出安装根的链接；允许的链接和执行权限须与宿主解包规则共同验收。需要签名的分发策略继续执行既有门禁，未经签名的包不能显示为“来源已验证”。

## 8 发布授权契约

### 8.1 独立发布凭据

市场新增发布工具专用凭据，明确绑定市场用户、当前开发者身份、一个或多个明确的插件 ID，以及允许的操作。首版通过市场网页登录后创建，令牌仅创建时显示一次；发布执行器保存于系统凭据存储，CI 接入后使用 CI secret。文件存储回退如需支持，须限制文件权限并排除版本控制。

当前 Bearer 登录会话继续服务现有接口，不据此声明已经支持发布专用令牌。新令牌不接受 PowerX Host API Key、实例登记凭据、插件业务登录态或市场共享开发令牌替代。

| 拟议 scope | 允许的操作 |
| --- | --- |
| `plugins:read` | 查询凭据范围内的插件、版本和发布资料选项 |
| `packages:write` | 上传插件平台包、查询自己上传操作的恢复结果 |
| `publications:read` | 查询凭据范围内的发布申请及送审操作结果 |
| `publications:submit` | 为已上传且归属明确的版本提交审核 |

首期凭据不授予创建插件、删除版本、人工批准或公开上架权限。令牌到期时间必须明确且受市场上限控制，默认及最长有效期在 M0 固定。首期不提供长期 refresh token 或自动续期。

### 8.2 服务端校验与撤销

每次请求检查令牌状态、有效期、用户状态、开发者成员关系及激活状态、插件归属和 scope。市场只保存可校验的令牌摘要和必要索引，不保存可重新导出明文的密钥。管理页面只显示名称、标识后缀、插件范围、scope、到期和最近使用时间。

上传结束、写入版本之前再次检查授权和归属。撤销或开发者停用后不得新增有效制品记录；已经提交的历史草稿和发布申请保留，后续状态迁移仍执行市场规则。进行中的请求与撤销操作以明确事务顺序决定是否完成，不能承诺撤销回滚已经完成的上传或卸载客户插件。

凭据创建和撤销沿用市场会话、Origin、CSRF 及本人权限。机器接口仅接受发布凭据，不接收 Cookie 作为机器授权；不为接入工具关闭现有浏览器 CSRF、来源或租户检查。

## 9 机器发布 API 草案

### 9.1 命名与兼容约定

候选协议名为 `powerx.plugin-publisher/v1`，候选路由组为 `<market_api_root>/publisher`，例如 `https://market.example/api/v1/publisher`。以下路径相对已配置的 API root，名称在 M0 冻结。

这组接口复用现有插件、Artifact 和 MarketPublication 服务及数据权威，新增独立认证和严格 DTO；不直接向插件暴露 `/internal/*` 管理入口。现有 `/dev/*` 浏览器接口保持请求及响应兼容。

| 方法与候选路径 | 用途 | 权限及阶段 |
| --- | --- | --- |
| `GET /publisher/discovery` | 发现协议、能力、限制和支持渠道 | 公开，无身份数据，M1 |
| `GET /publisher/me` | 读取绑定身份、scope、插件范围及到期时间 | 发布凭据，M1 |
| `GET /publisher/plugins/{plugin_id}` | 检查插件归属、名称及可用状态 | `plugins:read`，M1 |
| `GET /publisher/plugins/{plugin_id}/versions` | 分页读取版本与平台包 | `plugins:read`，M1 |
| `GET /publisher/plugins/{plugin_id}/versions/{version_id}` | 查询单个版本及完整制品集合 | `plugins:read`，M1 |
| `POST /publisher/plugins/{plugin_id}/package` | 流式上传单个平台包并登记草稿 | `packages:write`，M1 |
| `GET /publisher/operations/{operation_id}` | 恢复本人凭据范围内的写操作结果 | 对应写操作或读取 scope，M1/M2 |
| `GET /publisher/publication-options` | 读取市场允许的最低 Core 版本和许可证选项 | `plugins:read`，M2 |
| `POST /publisher/plugins/{plugin_id}/versions/{version_id}/submit` | 提交资料与完整制品集合审核 | `publications:submit`，M2 |
| `GET /publisher/plugins/{plugin_id}/publications` | 分页读取该插件审核及上架记录 | `publications:read`，M2 |

市场网页侧另需创建、列出、撤销本人发布凭据的接口和管理入口，候选资源为 `/dev/publish-tokens`，明文只出现在创建响应中。该管理资源不通过发布令牌访问。

### 9.2 Discovery

目标响应形状如下。示例为 M2 的能力组合，M1 仅声明已经实现的上传和恢复能力；数值以实际服务限制为准。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "service": "powerx-marketplace",
    "protocol": "powerx.plugin-publisher/v1",
    "features": ["package-upload", "idempotent-writes", "publication-submit"],
    "package_formats": ["zip", "tar.gz"],
    "max_package_bytes": 2147483648,
    "channels": ["stable"],
    "idempotency_retention_seconds": 604800
  }
}
```

幂等保留期示例为 7 天，最终值在 M0 固定，并作为服务端最低承诺。客户端连接时检查 service、protocol、feature、限制和允许渠道；404、协议不兼容或能力缺失时禁用相关远端动作，允许本地构建及手工上传，不猜测内部路由或改用共享凭据。

Discovery 只描述市场接收能力。构建平台集合由本地执行器另外返回；市场接受 `linux/arm64` 不代表当前执行器能够构建它。部署暂时关闭能力后，已接收的操作仍应可查询恢复结果。

### 9.3 上传请求和回执

请求使用 `Authorization: Bearer <发布凭据>`，`Idempotency-Key: <operation_id>`，`Content-Type: multipart/form-data`。客户端生成请求 ID，服务端返回可关联日志的 `X-Request-ID`。

| multipart 字段 | 要求 |
| --- | --- |
| `file` | 冻结安装包实际字节；不接受本地路径或 `file://` URI |
| `version` | 与计划及包内版本完全一致，拟限制最多 50 字符，不含前缀 `v` |
| `channel` | M1 只接受 `stable`，不能忽略不支持值后默认为 stable |
| `os`、`arch` | 与包内 target 及实际运行时一致 |
| `sha256` | 压缩文件的 64 位小写十六进制摘要 |
| `size` | 压缩文件字节数，必须与实际上传一致 |
| `release_notes` | 当前版本更新说明，最多 10000 字节 |

归属用户、开发者 ID、存储 key、可见性、审核者和上架状态不属于客户端可写字段。未知字段按明确契约拒绝。请求上限同时覆盖文件、multipart 开销、字段长度、解压预算和处理超时。

上传成功回执示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "operation_id": "1d11d7bd-9934-4b81-8807-494b39660d44",
    "plugin_id": "com.example.promo",
    "version_id": "87f8ac68-54da-4e3b-9e0e-fcce3c346f43",
    "version": "1.2.0",
    "artifact": {
      "artifact_id": "45cf4c3b-3562-4e66-9555-3530a02bb326",
      "os": "linux",
      "arch": "amd64",
      "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "size": 12345678
    },
    "market_version_url": "https://market.example/developer/plugins/com.example.promo?view=versions"
  }
}
```

摘要和大小仅作字段示例。成功表示市场已保存并登记对应包；版本当前是否仍为草稿需读取版本接口，不能把旧回执作为当前可写状态。机器响应不暴露对象存储路径、签名 URL 或其他开发者的私有资料。

市场链接必须属于配置市场的受信控制台 origin，子路径部署由市场明确配置；客户端不拼接固定域名，也不跟随任意外部详情地址。上传完成以服务端成功回执及查询结果为准，执行器发送进度达到 100% 时页面显示“市场校验中”。

### 9.4 送审请求

候选机器送审请求封装为 `metadata` 与 `expected_artifacts`，区别于现有浏览器接口的扁平资料体；两者在市场服务层归一化，不修改旧接口形状。

`metadata` 复用现有资料字段：`description`、`license`、`min_core`、`support_url`、可选 `icon_url`、`security_statement` 和 `privacy_statement`。最低 Core 版本及许可证来自 publication options，不制造默认选项。描述、安全和隐私说明各至少 10 个字符、至多 10000 字节，URL 和标识限制继续沿用市场校验。

`expected_artifacts` 为页面已经展示并由开发者选择送审的完整平台包集合，每项包含 `artifact_id/os/arch/sha256/size`。对象引用使用市场返回的 Artifact UUID，平台及摘要不得代替对象引用。市场在提交事务中核对集合一致性，逐包验证归属、可读性、大小、摘要、包内身份及目标，并绑定不可变集合快照。集合发生变化时拒绝，返回重新读取提示。

完整集合快照必须持久化，管理员审核、包查看及公开上架服务统一读取并复核这份快照，不能只在机器接口接收时检查一次。现有浏览器入口保持 DTO 形状，由服务端构造和绑定集合。历史申请不补造已验收快照；P07 需明确缺少快照时的阻断和显式复核步骤，不默认添加旧格式兼容。

M2 首次验收使用一个平台包，但服务端不能只验证 Version 主制品后放行其他已挂载包。缺少安全扫描报告显示“未提供”或“未执行”，已有阻断报告继续阻断；扫描和签名策略是否强制执行由既有市场政策决定。

送审回执包含 `operation_id/publication_id/version_id/status/submitted_at/market_publication_url`。状态为 `submitted` 只表示已入审核流程。审核批准与公开上架继续由有权限的市场人员执行。

### 9.5 分页和状态读取

机器列表使用有界分页，拟议 `page/size`，响应 `items/total/page/size`，默认 20、最大 100，M0 固定。返回完整版本平台集合及状态；不能沿用当前最多 200 条后让客户端误认为取得全部历史。

状态只读接口给出市场版本、申请状态及真实时间，不返回凭据或存储位置。页面在任务期间、重新打开分区及手工刷新时更新，审核等待期间采用有界刷新策略，不新增无上限轮询。

## 10 幂等与断网恢复

M1 的“断网恢复”指恢复任务、核对服务端结果，以及必要时用原 operation ID 和同一冻结文件整包重传。不包含字节偏移、分片会话或断点续传；本协议没有此类接口，页面和指南不得承诺已传字节可以续传。

### 10.1 写操作身份

客户端在发送上传或送审之前，将 UUID 操作 ID 和规范化请求摘要原子落盘。网络重试必须复用该操作 ID、同一文件及同一业务内容。

市场将操作绑定到稳定的市场用户、开发者、插件及操作类型；凭据 ID 用于审计，不单独决定幂等身份。换发凭据后，只有仍具有同一身份、资源范围和操作权限的调用方才能恢复原操作。

| 情况 | 拟议行为 |
| --- | --- |
| 同操作 ID、同内容，已成功 | 返回同一业务结果，不重复登记版本、Artifact 或送审记录 |
| 同操作 ID、同内容，仍处理 | 返回处理中及重试提示，客户端查询同一 operation |
| 同操作 ID、同内容，已失败 | 确定性失败返回原结果；可恢复失败由服务端接管同一操作，不另建业务记录 |
| 同操作 ID、不同内容 | `409 idempotency_conflict`，禁止重放或覆盖 |
| 不同操作 ID、同版本同平台 | 返回明确的现有包冲突，不能据此直接判为本次上传成功 |
| 响应丢失 | 查询本人 operation，再核对版本及平台包；确认失败或不存在后才决定重传 |
| 幂等记录超过承诺保留期 | 显示需要核对，查询版本及摘要；不能自动变更 key 后覆盖现有包 |

机器接口采用上传成功 201、同操作成功重放 200、处理中 202；送审也遵循对应语义。202 必须包含 operation ID、状态查询信息及 `Retry-After`，不显示“上传完成”。

操作查询至少返回 `operation_id/type/plugin_id/status/created_at/updated_at`，状态区分 `processing/succeeded/failed`；成功返回原业务回执，失败返回脱敏错误码及可重试性。该状态描述这次写操作，不能代替版本当前审核状态。请求指纹包含版本、平台、文件摘要和大小、渠道及更新说明，送审还包含规范化资料和完整制品集合。

操作查询 404 仅说明查询时未找到本人可见操作，不能证明仍在传输中的原请求不会稍后到达。随后仅可使用原操作 ID 重试，由服务端在并发请求中去重；不得换 key 规避结果不明。

### 10.2 存储与数据库一致性

对象存储、数据库和操作记录之间不能假定存在分布式事务。市场采用唯一制品 key、插件及版本锁、唯一约束和操作记录控制并发。版本或 Artifact 登记失败时，已写入对象进入可重试的所属清理记录，不能留下可被公开分发的孤立登记。

“成功”要求最终业务登记和操作结果可靠保存。进程在对象写入后、数据库提交前后退出均须可恢复；操作处理中状态需要租约或明确的接管机制，不能永久卡在 processing。清理仅触及该次操作拥有且未被引用的对象，不能删除已登记或其他任务复用的字节。

取消发生在本地构建期间时终止所属进程；发生在上传期间时停止客户端传输并标记“结果待核对”，通过 operation 及版本查询确认是否已经保存。取消上传不等于删除市场草稿。送审成功后关闭页面不撤回申请。

## 11 任务和发布状态

### 11.1 本地任务阶段

正常阶段为 `queued → prechecking → building → packing → verifying → ready → uploading → uploaded`。M2 选择自动送审时继续 `submitting → submitted`。

任务另有 `failed/cancelled/interrupted/reconciling` 状态，记录发生阶段及可重试动作。市场写操作结果不明时进入 `reconciling`，不得仅根据 HTTP 超时显示“上传失败，可直接重建覆盖”。

本地构建成功、传输完成、市场登记成功和市场公开分别有独立判据。日志保留详细诊断，产品页面显示阶段、原因及下一步；日志先脱敏，再提供下载。

### 11.2 市场状态与允许动作

| 市场状态 | 页面含义 | 发布工具允许动作 |
| --- | --- | --- |
| 尚无市场版本 | 仅有本地计划或构建 | 构建、上传 |
| `draft` | 私有草稿 | 查询、送审；后续阶段可追加不存在的平台包 |
| `submitted` | 待审核 | 查询资料与进度，不追加或替换平台包 |
| `rejected` | 资料或审核被驳回 | 展示原因、修改资料后重新送审；包变更沿用显式版本规则 |
| `approved` | 已批准，等待市场上架 | 查询，不显示为公开，不替换包 |
| `published` | 市场已公开 | 查询、跳转；修复制品应创建更高版本 |
| 删除清理中等维护状态 | 资源暂不可写 | 清楚显示原因；发布工具首期不代执行删除 |

当前市场允许 rejected 版本追加新目标而不覆盖旧目标。M2 重新送审必须明确展示并绑定新的完整集合；重新送审不抹去既有审计。修复已有目标包的字节采用新版本，不能暗中替换已审查的文件。

## 12 版本和渠道规则

首期版本遵循 SemVer，例如 `1.2.0`，包内版本不包含 `v`。`v1.2.0` Git 标签如后续需要，单独记录，不自动创建。构建元信息 `+build` 不会提升 SemVer 优先级，不把它当作可绕过“新上架版本必须更高”的补丁号。

市场版本唯一性沿用 `(plugin_id, version)`；`stable/beta` 不能在同一版本下产生两条独立版本记录。第一期上传显式 `stable`，正式版本才可走稳定渠道公开。需要测试版本时先保留本地产物，不以虚假稳定版本宣称 beta 发布已支持。

M3 增加 beta 时，双方先对齐：预发布 SemVer、渠道内最新版本排序、当前全插件比较逻辑的兼容、公开目录筛选、宿主按渠道发现及未来 promotion 规则。首版不设计 `1.2.0-beta.1` 改名为 `1.2.0` 后仍视为同一安装包，因为包内版本发生变化必须重新生成并审核。

市场最低 Core 版本目前是精确版本选项；更复杂的 Core 范围、Framework 版本范围和依赖矩阵作为后续契约扩展，首期不向现有字段写入 `>=1.0.0` 一类未被支持的表达式。

## 13 错误与降级

以下为机器协议拟议错误映射，现有浏览器错误码保持兼容。最终名称、响应 schema 及可重试性随 OpenAPI 一起冻结。

| HTTP 与错误码 | 含义 | 客户端动作 |
| --- | --- | --- |
| 400 `invalid_input` | 字段、版本、元数据或格式无效 | 保留表单并定位字段，不自动重试 |
| 400 `package_plugin_id_mismatch` | 包内 ID 与登记插件不符 | 展示两者，修正构建或选择目标 |
| 400 `package_target_mismatch` | 包、请求或运行时目标不符 | 阻断上传或登记，重新构建 |
| 401 `publisher_unauthorized` | 凭据缺失、过期或撤销 | 暂停写操作，重新绑定后核对原操作 |
| 403 `publisher_forbidden` | scope、成员或开发者状态不满足 | 提示权限原因，不切换其他身份重试 |
| 404 `not_found` | 当前身份下插件、版本或操作不可见 | 核对本人的绑定与资源，不泄露外部资源存在性 |
| 409 `artifact_conflict` | 该版本及平台已有包 | 查询并比对，禁止覆盖；修改字节须新版本 |
| 409 `version_locked` | 版本已提交、批准或上架 | 读取当前状态，创建新版本 |
| 409 `idempotency_conflict` | 同操作 ID 对应不同内容 | 保留证据，纠正任务状态，不自动换 key |
| 409 `artifact_set_changed` | 送审集合已变化 | 重新读取并展示完整集合，再由用户送审 |
| 409 `artifact_changed` | 存储内容与登记记录不一致 | 阻断送审或上架，核对原制品 |
| 409 策略错误 | 许可证、安全、渠道或版本排序不满足 | 展示市场原因，不伪造通过结果 |
| 413 `package_too_large` | 文件或处理预算超过限制 | 展示 discovery 限制，调整产物 |
| 429 | 触发限流 | 遵守 Retry-After，有上限退避 |
| 503 或网络异常 | 服务不可用或结果未知 | 优先恢复查询；仅用同 key、同内容有界重试 |

市场维护或机器协议不可用时，保留本地构建及产物导出能力。可以引导开发者进入市场现有上传页面，但不自动回退到内部 API、关闭鉴权或直接写对象存储。重试耗尽保留可恢复任务，错误中给出操作 ID 和请求 ID，不包含凭据、完整本机路径或私有存储地址。

## 16 实施阶段与发布顺序

| 阶段 | 范围 | 退出标准 |
| --- | --- | --- |
| M0 文档及协议对齐 | 确定运行架构、命令迁移、授权、路由、包布局、版本规则和错误 | 第 18 节逐项有结论；OpenAPI 与共享样例经双方 Review |
| M1 单平台上传闭环 | 凭据管理、机器上传及幂等、版本查询、Framework 本地工具和页面 | 独立生成插件构建真实单平台包，上传后私有草稿可见，断网和刷新可恢复 |
| M2 送审闭环 | 发布资料选项、完整集合验证、送审及进度回显 | 真实提交、驳回后补资料、批准仍私有、显式上架后公开和可下载 |
| M3 多平台与渠道 | 批量平台构建、逐包任务、beta 及渠道发现 | 不覆盖包，不混用源码快照；全部目标齐备才送审；渠道规则一致 |
| M4 CI 接入 | 同引擎非交互执行、CI secret、可追踪回执 | CI 与页面对同一协议产生一致结果，记录构建源和运行工件 |

依赖顺序为市场契约和机器接口先就绪，Framework 再按冻结协议接入。双方可以在受控 fixture 上并行实现，但真实联调必须等待对应接口和实际包可用。

发布时先运行市场增量迁移，部署机器接口及凭据管理，再发布或分发可追踪的 Framework/CLI 包，随后生成插件验证并启用页面。SDK、本地快照、市场部署和客户安装分别记录版本及状态。

回退时先关闭 discovery 对应能力和新写操作，保留操作结果查询、浏览器管理及已存在数据；Framework 禁用远端动作并保留产物。客户端对能力关闭先重新发现，不改用旧内部发布 API。数据库保留可兼容的新增表及记录，不通过回退删除审核、包或审计；未完成操作按恢复规则收敛。

市场上架回退、客户实例降级和迁移回滚分别属于现有业务流程。发布工具不能通过上传旧版本覆盖当前版本来实现回滚。

证据分为源码及契约检查、受控测试、独立生成插件消费、真实市场上传、人工审核及公开下载、真实 PowerX 安装启用。M1 不覆盖真实安装，M2 的下载成功也不代替宿主启用；只有单独执行最后一项后才能报告客户安装链路通过。

临时验证使用隔离账号、数据库及存储或明确归属的测试资源，记录自己启动的 PID、工作目录、监听端口和会话。结束停止所属服务及子进程、确认端口释放，按归属清理测试数据并保留必要审计；不得重启或停止用户已有服务。前端实现完成相关 ESLint、回归、类型检查及构建，并实际完成浏览器验收。
